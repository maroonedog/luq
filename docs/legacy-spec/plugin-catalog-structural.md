# plugin-catalog-structural

The previous implementation had 15 structural plugins directly under
`src/core/plugin/`: five for arrays, eight for objects, one tuple and one
recursive. Every one was made with
`plugin({name, methodName, allowedTypes, category, impl})`, and every `impl`
returned the same "hoisted validator" shape:
`{ check(value, allValues?), code, getErrorMessage(value, path, allValues?), params }`.

The core of the semantics is a two-layer arrangement: when a value is not of
the target type, `check` returns `true` and lets it pass, and checking the type
itself is the job of the `arrayType` / `objectType` validators that field-context
injects automatically per type slot (`b.array`, `b.object`). Only
`arrayContains`, `objectPropertyNames` and `objectPatternProperties` broke that
convention, returning `false` for a value of the wrong type.

Applying rules to array elements was expressed in the path grammar rather than
by a plugin: `field[*]`, `field[*].prop`, `field[*][*]`. The path type
`NestedKeyOf` behind `v()` permitted only `items`, `items[*]` and
`items[*].name`; `items.name` was a compile error.

Four things demonstrably worked: array-level constraints; single-level scalar
element validation `a[*]`; single-level element-field validation `a[*].prop`,
with the error path `a[0].prop`; and an array-level constraint inside an
element, `a[*].b`. Against that, `a[*][*]` (multi-dimensional) validated
nothing at all, silently. Two levels of nesting, `a[*].b[*].prop`, dropped the
outer index — the path came out `a.b[0].prop` — and returned the wrong code
(`required`). `tupleBuilder` failed at `build()` with a TypeError.

Recursion went through `objectRecursivelyPlugin`'s marker form,
`recursively("__Self" | "__Element")`, with a default `maxDepth` of 10 and a
WeakSet cutting off cycles. `__Self` worked on a standalone object; on an array
element path, `recursively("__Self")` failed.

On top of all that, `attachPluginMethods` in field-context swallowed every
exception thrown while constructing a plugin, so an argument guard — a negative
`minLength`, for instance — never reached the user at all.

## Contracts to preserve (17)

### must-preserve (11)

#### arrayMinLengthPlugin
- Source: `src/core/plugin/arrayMinLength.ts`
- Shape: export const arrayMinLengthPlugin; name="arrayMinLength", methodName="minLength", allowedTypes=["array"], category="standard"; impl(minLength: number, options?: ValidationOptions<{min:number; actual:number}>)
- Meaning: check: anything that is not an array, null and undefined included, passes as true. For an array, `value.length >= minLength`. The code defaults to "arrayMinLength" and `options.code` overrides it, which a test demonstrates. The default message is `Array must have at least ${min} elements, but got ${actual}`, and the extra context reaching messageFactory is `{min, actual}`, where `actual` is 0 for a non-array. The implementation throws `Error(\`Invalid minLength: ${x}\`)` for a non-number or a negative, but NaN passes the guard — and the throw is swallowed by attachPluginMethods' try/catch, so it never reaches the user.

#### arrayMaxLengthPlugin
- Source: `src/core/plugin/arrayMaxLength.ts`
- Shape: export const arrayMaxLengthPlugin; name="arrayMaxLength", methodName="maxLength", allowedTypes=["array"], category="standard"; impl(maxLength: number, options?: ValidationOptions<{max:number; actual:number}>)
- Meaning: check: a non-array passes as true. For an array, `value.length <= maxLength`. The code defaults to "arrayMaxLength" and the message to `Array must have at most ${max} elements, but got ${actual}`, with `{max, actual}` as extra context. Same argument guard as arrayMinLength, and the same swallowing.

#### arrayUniquePlugin
- Source: `src/core/plugin/arrayUnique.ts`
- Shape: export const arrayUniquePlugin; name="arrayUnique", methodName="unique", allowedTypes=["array"], category="standard"; impl(options?: ValidationOptions)
- Meaning: check: a non-array passes as true. Duplicates are decided with `===` rather than SameValueZero — a double loop up to length 10 and a Set above it. That makes the answer depend on length: NaN is not equal to itself under `===` but is under a Set, while 0 and -0 are equal under both. (A test asserting that 0 and -0 count as the same currently fails.) Object elements are compared by reference only. The code defaults to "arrayUnique" and the message to "Array must contain unique values", which names no duplicate value.

#### arrayIncludesPlugin
- Source: `src/core/plugin/arrayIncludes.ts`
- Shape: export const arrayIncludesPlugin; name="arrayIncludes", methodName="includes", allowedTypes=["array"], category="arrayElement"; impl<TElement = any>(element: TElement, options?: ValidationOptions)
- Meaning: check: a non-array passes as true. For an array, `Array.prototype.includes(element)`, which is SameValueZero — so an array containing NaN satisfies `includes(NaN)`, and objects compare by reference. The code defaults to "arrayIncludes" and the message to `Array must include ${JSON.stringify(element)}`, with `{element}` as extra context. The declared category is "arrayElement" while the documentation says "standard", and the behaviour is identical to every other standard plugin; category carries almost no meaning as things stand.

#### objectMinPropertiesPlugin
- Source: `src/core/plugin/objectMinProperties.ts`
- Shape: export const objectMinPropertiesPlugin; name="objectMinProperties", methodName="minProperties", allowedTypes=["object"], category="standard"; impl(minValue: number, options?: ValidationOptions)
- Meaning: JSON Schema's `minProperties`. check: passes as true when `typeof value !== "object" || value === null` — which means an array, being an object, does get counted. `Object.keys(value).length >= minValue`, own enumerable keys only. The code defaults to "objectMinProperties" and the message to `Must have at least ${min} properties, but has ${actual}`, with `{min, actual}` as extra context. It throws for a non-number, NaN or a negative, and that throw is swallowed too.

#### objectMaxPropertiesPlugin
- Source: `src/core/plugin/objectMaxProperties.ts`
- Shape: export const objectMaxPropertiesPlugin; name="objectMaxProperties", methodName="maxProperties", allowedTypes=["object"], category="standard"; impl(maxValue: number, options?: ValidationOptions)
- Meaning: JSON Schema's `maxProperties`, symmetrical with objectMinProperties: a non-object or null passes, and `Object.keys(value).length <= maxValue`. The code defaults to "objectMaxProperties" and the message to `Must have at most ${max} properties, but has ${actual}`, with `{max, actual}` as extra context.

#### objectAdditionalPropertiesPlugin
- Source: `src/core/plugin/objectAdditionalProperties.ts`
- Shape: export const objectAdditionalPropertiesPlugin; name="objectAdditionalProperties", methodName="additionalProperties", allowedTypes=["object"], category="standard"; impl(allowed: boolean | JSONSchema7, options?: { allowedProperties?: string[]; additionalPropertiesSchema?: JSONSchema7; strict?: boolean } & ValidationOptions)
- Meaning: JSON Schema's `additionalProperties`. The set of known properties is not derived; it has to be listed in `options.allowedProperties`, and omitting it makes every key "additional". `strict = (allowed === false || options.strict === true)`, and strict requires `extraProperties.length === 0`. When `allowed` is an object, or `options.additionalPropertiesSchema` is given, each additional property is checked one at a time against a cut-down subset: `type` (string/number/boolean/object/array), `minLength`/`maxLength` for strings, and `minimum`/`maximum` for numbers, and nothing else. `allowed === true` or unset always passes; a non-object or null passes. The code defaults to "objectAdditionalProperties"; the default message is `Additional properties are not allowed: ${extraProperties.join(", ")}` under strict and `Additional properties validation failed` otherwise, with `{extraProperties: string[]}` as extra context.

#### objectDependentRequiredPlugin
- Source: `src/core/plugin/objectDependentRequired.ts`
- Shape: export const objectDependentRequiredPlugin; name="objectDependentRequired", methodName="dependentRequired", allowedTypes=["object"], category="standard"; impl(dependencies: Record<string, string[] | { required: string[]; message?: string }>)
- Meaning: JSON Schema's `dependentRequired`. `check(value, allValues)` uses `allValues` when it is given and `value` otherwise, so that it can apply at the root. When a trigger property is `in` the object and not undefined, every dependent property must be `in` it and not undefined. A non-object, an array or null passes as true. Applying it at the root — `.v("", b => b.object.dependentRequired({...}))` — works, and the error path is `""`. The code is `"DEPENDENT_REQUIRED"`, with no options and no override. The message joins, with "; ", either a custom message or `When '${trigger}' is present, the following properties are required: ${missing.join(", ")}` per violation, prefixed with `${path}: ` when the path is non-empty.

#### objectRecursivelyPlugin, also exported as recursivelyPlugin
- Source: `src/core/plugin/objectRecursively.ts`, `src/core/builder/validator-factory.ts`
- Shape: export const objectRecursivelyPlugin; name="recursively" — the one plugin name with no `object` prefix — methodName="recursively", allowedTypes=["object"], category="standard"; impl(targetFieldPath: "__Self" | "__Element", options?: { maxDepth?: number } & ValidationOptions<{targetPath}>). Also `export const RECURSIVE_SELF = "__Self"` and `export const RECURSIVE_ELEMENT = "__Element"`.
- Meaning: a marker plugin that validates nothing. `check` always returns true and instead attaches `__isRecursive: true` and `recursive: { targetFieldPath, maxDepth }` to its result. `maxDepth` defaults to 10, the code to "recursively", and the message — never actually emitted — to `Recursive validation for ${targetFieldPath}`. The recursion itself is done by `createRecursiveValidator` in validator-factory: it stops without an error past `maxDepth`; stops without an error on a cycle, detected with a WeakSet; applies only the original validators (optional/nullable) to null and undefined without recursing; for `"__Self"` applies every field validator except its own to the nested object, rewriting error paths to `${currentPath}.${error.path}` and recursing one level deeper on any field carrying the recursion marker; and for `"__Element"` applies every field validator not containing `[*]` to each array element, with paths `${currentPath}[${i}].${error.path}`. Measured: `__Self` on a standalone object (a tree node's parent/left/right) works and produces paths like `parent.name`. `recursively("__Self")` on an array element path such as `categories[*]` fails.

#### The array element path syntax `[*]`, which is v()'s path language rather than a plugin
- Source: `src/types/util.ts`, `src/core/builder/nested-array-processor.ts`, `src/core/builder/array-batch-optimizer.ts`
- Shape: the forms `NestedKeyOf<T>` produces: `items`, `items[*]`, `items[*].prop`, `items[*][*]` for two dimensions, and `items[*].sub[*].prop` for deeper nesting. `TypeOfPath<T, Path>` resolves the corresponding element type. `items.prop`, reaching an element through dot notation, is a type error.
- Meaning: an array-level constraint and element validation are composed as separate `v()` calls: `.v("users", b => b.array.required().minLength(1))` alongside `.v("users[*].name", b => b.string.required().min(2))`. What was confirmed to work: `users[*].name` produces the error path `users[0].name` and keeps the plugin's own code, such as `stringMin`; `tags[*]`, validating a scalar element directly, produces `tags[1]`; an array-level constraint inside an element, `minLength` on `users[*].addresses`, produces the path `users[0].addresses` with code `arrayMinLength`; an empty array runs the element validators not once, only the array-level ones; and a non-array value produces the injected `arrayType`'s code `"VALIDATION_ERROR"` and message `"Expected array"`.

#### The structural type check a type slot injects automatically (arrayType / objectType)
- Source: `src/core/builder/context/field-context.ts`
- Shape: `createFieldContext(path, plugins)` puts a validator at the front unconditionally when it builds `b.array` or `b.object`. arrayType: `check = (v == null ? true : Array.isArray(v))`, `messageFactory = () => "Expected array"`. objectType: `check = (v == null ? true : typeof v === "object" && v !== null && !Array.isArray(v))`, `messageFactory = () => "Expected object"`. `b.tuple` and `b.union` get no automatic type check; the factory returns null for them.
- Meaning: "choosing `b.array` is what checks that it is an array" is the premise behind every array plugin passing a non-array through. null and undefined pass here and are decided by required / optional / nullable. In the emitted error, though, the code flattens to `"VALIDATION_ERROR"` and the plugin's name is lost.

### should-preserve (6)

#### arrayContainsPlugin
- Source: `src/core/plugin/arrayContains.ts`
- Shape: export const arrayContainsPlugin; name="arrayContains", methodName="contains", allowedTypes=["array"], category="standard"; impl(schema: unknown | ContainsSchema | JSONSchema7). Also `export interface ContainsSchema { validator: (value:any)=>boolean; message?: string }`.
- Meaning: Draft-07's `contains`. The argument takes three forms: a primitive, array or null becomes `value.includes(schema)`, meaning at least one exactly equal element; `{validator, message?}` becomes `value.some(validator)`; and a JSONSchema7 object becomes `value.some` against a built-in cut-down checker. That checker looks at `type` (string/number/boolean/array/object/null), `minLength`/`maxLength`/`pattern` for strings, `minimum`/`maximum`/`multipleOf` for numbers, `enum` and `const`, and ignores everything else. Unlike the other array plugins it returns false for a non-array rather than passing it through. The code is `"ARRAY_CONTAINS"` — the only SCREAMING_SNAKE one — and it accepts neither options nor a code override. The messages are `${path} must contain ${JSON.stringify(schema)}`, `schema.message ?? \`${path} must contain at least one matching item\`` and `${path} must contain at least one item matching the schema` for the three forms.

#### objectPlugin
- Source: `src/core/plugin/object.ts`
- Shape: export const objectPlugin; name="object", methodName="object", allowedTypes=["object"], category="standard"; impl(options?: ValidationOptions)
- Meaning: check: `value !== null && typeof value === "object" && !Array.isArray(value)` — a plain-object test that Date, Map and RegExp pass. Unlike the other structural plugins it does not pass null and undefined through; undefined is `typeof "undefined"` and fails. The code defaults to `"type_mismatch"`, the only snake_case one where the rest are camelCase, and the message to `"Not an object"`, which contains neither the path nor the value. It duplicates the role of the `objectType` validator that the `b.object` slot injects, which passes null and undefined through and says `"Expected object"`.

#### objectPropertyNamesPlugin
- Source: `src/core/plugin/objectPropertyNames.ts`
- Shape: export const objectPropertyNamesPlugin; name="objectPropertyNames", methodName="propertyNames", allowedTypes=["object"], category="standard"; impl(schema: RegExp | string | PropertyNamesSchema). Also `export interface PropertyNamesSchema { validator: (name:string)=>boolean; message?: string }`.
- Meaning: JSON Schema's `propertyNames`. Every key must satisfy a RegExp, tested as it is; a string, from which a `new RegExp(str)` is built on every call; or `{validator}`. Anything that is none of those three returns false. A non-object, an array or null returns false rather than passing through, which is asymmetrical with the other object plugins. It accepts neither options nor a code override, and the code is `"PROPERTY_NAMES"`. The message is `schema.message` when present, otherwise `${path} has invalid property names: ${invalidNames.join(", ")}. Property names must match ${patternDesc}`, where `patternDesc` is the RegExp's `toString()`, `/str/` for a string, and `"the specified pattern"` otherwise.

#### objectPatternPropertiesPlugin
- Source: `src/core/plugin/objectPatternProperties.ts`
- Shape: export const objectPatternPropertiesPlugin; name="objectPatternProperties", methodName="patternProperties", allowedTypes=["object"], category="standard"; impl(patterns: PatternPropertiesSchema). Also `export type PatternPropertiesSchema = Record<string, ((value:any)=>boolean) | PatternValidator>` and `export interface PatternValidator { validator:(value:any)=>boolean; message?: string }`.
- Meaning: close to JSON Schema's `patternProperties` but meaning something different. For each property name it walks the patterns in declaration order, applies the check of the FIRST one that matches, and breaks — where JSON Schema applies every matching pattern, so this is not conformant. A property matching no pattern is unconditionally valid. Values are checked by a function or `{validator}`. A non-object, an array or null returns false. No options, no code override; the code is `"PATTERN_PROPERTIES"`. The message collects, per violation, `${prop}: ${customMessage}` or `${prop} (matching pattern ${patternString}) has invalid value` into `${path} has pattern property violations: ${errors.join(", ")}`, falling back to `${path} has invalid pattern properties`. Patterns are recompiled with `new RegExp` on every call.

#### objectDependentSchemasPlugin
- Source: `src/core/plugin/objectDependentSchemas.ts`
- Shape: export const objectDependentSchemasPlugin; name="objectDependentSchemas", methodName="dependentSchemas", allowedTypes=["object"], category="standard"; impl(schemas: Record<string, JSONSchema7 | { validator:(value:any)=>boolean; message?: string }>)
- Meaning: JSON Schema's `dependentSchemas`, with the same `allValues`-first logic as dependentRequired. When the trigger property is present, a `{validator}` is called with the whole object, and a JSONSchema7 goes through a built-in cut-down checker applied to the whole object. That checker looks at `type === "object"`, `required[]`, and for each subschema directly under `properties` its `type` plus (`minLength`/`maxLength`/`pattern` for strings, `minimum`/`maximum` for numbers, `minItems`/`maxItems` for arrays), `enum` and `const`. It descends one level and does not recurse. A non-object, an array or null passes through. The code is `"DEPENDENT_SCHEMAS"`. The message is `When '${trigger}' is present, the following properties are required: ${missing.join(", ")}` when something required is missing, and for a custom validator `schema.message ?? \`Schema validation failed when '${trigger}' is present\``, with the same path prefixing as dependentRequired.

#### tupleBuilderPlugin
- Source: `src/core/plugin/tupleBuilder.ts`, `src/core/builder/plugins/composable-plugin.ts`
- Shape: export const tupleBuilderPlugin = createComposableDirectlyPlugin<"tupleBuilder","builder",readonly ["tuple"], unknown[]>(...); name="tupleBuilder", methodName="builder" — so it is called as `b.tuple.builder(...)` — allowedTypes=["tuple"], category="composable-directly". builder(...builderFns, options?: { rest?: (ctx)=>any; messageFactory?: { notArray?, lengthMismatch?, tooShort? } })
- Meaning: the intended semantics are a fixed-length tuple, each element with its own builder, plus an optional rest element. The last argument counts as options when it carries a `rest` property or is an empty object. Element builders are built in advance against a FieldContext at `${fieldPath}[${i}]`, and the rest builder is built once at `${fieldPath}[rest]` and reused for every surplus element. Validation: a non-array gives code TUPLE_NOT_ARRAY and "Value must be an array"; without a rest, `length !== tupleLength` gives TUPLE_LENGTH_MISMATCH and `Tuple must have exactly ${expected} elements, got ${actual}`; with a rest, `length < tupleLength` gives TUPLE_TOO_SHORT and `Tuple must have at least ${expected} elements, got ${actual}`. Each fixed element is checked with `validator.validate(value[i], value)`, passing the array itself as `allValues`, and error paths are rewritten to `${fieldPath}[${i}]`. An empty error array falls back to code ELEMENT_INVALID and `Validation failed for element ${i}`. Rest elements from `tupleLength` onward go through the rest validator under the same path rule. `builder()` is assumed to be called once and only `compositions[0]` is used; with no arguments it becomes a validator that always returns false. Measured: `.v("loc", b => b.tuple.required().builder(...))` fails at `build()` with `TypeError: Cannot read properties of undefined (reading 'addValidator')`, composable-plugin.ts touching a `builder._executionPlan` that does not exist — so this API does not work at all.

## Behavioural rules

- Every plugin implementation has the same shape: `impl(...args)` returns `{ check(value, allValues?): boolean, code: string, getErrorMessage(value, path, allValues?): string, params: unknown[] }`. It has no side effects and rewrites no value. Separating a pure check from lazy message construction is worth carrying forward: the message string is only assembled on failure.
- An array or object constraint passes a value of the wrong type through (`check` returns true). The type itself is decided by the `arrayType` / `objectType` validator the slot injects. The exceptions are arrayContains, objectPropertyNames and objectPatternProperties, which return false for the wrong type, and objectPlugin, which returns false for undefined. This convention should hold for every plugin.
- null and undefined are not a structural plugin's business; required / optional / nullable decide them. Measured: passing null to `b.array.optional()` gives code "optional" and `items cannot be null (use undefined for optional fields)`, optional permitting only undefined. `b.array.nullable()` lets null through.
- An array-level constraint and element validation are composed as separate `v()` calls. `b.array.minLength(3)` acts on the array alone, and element validation is declared on the separate path `field[*]` or `field[*].prop`. There is no API for composing element validators inside one chain; tupleBuilder is the sole exception, taking child builders.
- In an element path's error, the declared `[*]` is replaced by the real index at run time: `users[*].name` emits `users[0].name`, and `tags[*]` emits `tags[1]`. The element error keeps the element plugin's own code, such as stringMin or numberMin.
- Element validators are not run at all against an empty array. Only the array-level validators run.
- Several validators on one field stop at the first failure by default, `abortEarlyOnEachField` defaulting to true. Measured: `["b","b"]` against `.includes("a").unique()` returns the arrayIncludes error alone and never reports arrayUnique. While iterating array elements, though, `abortEarlyOnEachField` is forcibly overridden to false and every field of one element is validated.
- Element paths are reorganised into "array batches" at run time: `parseArrayElementPath` breaks `a[*].b`, `a.*.b`, `a[*]` and `a[*][*]` into `{ arrayPath, elementField }`; `buildNestedArrayHierarchy` builds a tree carrying parent-child relations and depth; and the array is walked once, validating every element field together. Element field accessors are compiled in advance. Reading an array once and batch-validating all its element fields is worth carrying forward.
- Recursion has exactly two keywords, `recursively("__Self")` and `recursively("__Element")`. A branch taking an arbitrary field path exists in the code, but the published type is narrowed to `RecursiveKeyword`. `maxDepth` defaults to 10, and both exceeding the depth and detecting a cycle (WeakSet) are silent stops rather than errors.
- `__Self` means "apply every field rule declared for the root type to this nested object again", skipping only its own field path to prevent infinite recursion. `__Element` means "apply every field rule of the root type, excluding those containing `[*]`, to each array element".
- Reading a JSON Schema (`fromJsonSchema`) tries to resolve the structural keywords as: minItems → chain.minItems, maxItems → chain.maxItems, uniqueItems → chain.unique(), items as an array → chain.tupleBuilder(...), minProperties → chain.minProperties, maxProperties → chain.maxProperties, additionalProperties → chain.additionalProperties, propertyNames → chain.propertyNames. But no `minItems`, `maxItems` or `tupleBuilder` method exists — the real method names are minLength, maxLength and builder — so those branches fall through the `&& chain.minItems` existence check in silence and apply nothing. The mapping from keyword to method name should be one source of truth.
- The tree-shaking unit is one plugin, one file, one named export, with `./plugins/<name>` subpaths in package.json's exports lining up one to one (arrayMinLength, arrayMaxLength, arrayUnique, arrayIncludes, arrayContains, object, objectMinProperties, objectMaxProperties, objectAdditionalProperties, objectPropertyNames, objectPatternProperties, objectDependentRequired, objectDependentSchemas, tupleBuilder). objectRecursively and unionGuard have no subpath and are not exported from `src/index.ts` either, only from `core/plugin/index.ts`. That gap should be closed.
- `allowedTypes` is the only gate deciding which type slot a method appears on: `["array"]` for the array family, `["object"]` for the object family, `["tuple"]` for tupleBuilder. A slot not in `allowedTypes` grows no method, and the type level excludes it through `FilterPluginsByType` as well.
- `TypeName` has ten values: string, number, date, array, union, tuple, object, boolean, null, any. The slots are `b.string`, `b.number`, `b.boolean`, `b.date`, `b.array`, `b.object`, `b.tuple` and `b.union`. tuple and union get no injected type check.

## Not carried forward

- **The `try { ... } catch (e) { /* Plugin error - ignore silently */ }` in field-context's attachPluginMethods.** It swallows every exception thrown while a plugin is constructed, so an argument guard such as `arrayMinLength(-1)` or `objectMinProperties(NaN)` never reaches the user — and worse, the validator is never pushed onto the validators array, so **the rule quietly disappears**. Two tests asserting that a negative minimum length and a non-numeric maximum length throw fail because of this. A configuration mistake must fail at build time.
- **Error codes named inconsistently**: camelCase (arrayMinLength, objectMinProperties) alongside SCREAMING_SNAKE (ARRAY_CONTAINS, PROPERTY_NAMES, PATTERN_PROPERTIES, DEPENDENT_REQUIRED, DEPENDENT_SCHEMAS, TUPLE_NOT_ARRAY) alongside snake_case (type_mismatch). An error code is a published contract users switch on. One rule, and camelCase matching the plugin's name is the one to pick.
- **Plugins that accept no options, no code override and no messageFactory** (arrayContains, objectPropertyNames, objectPatternProperties, objectDependentRequired, objectDependentSchemas). Within one catalog, some accept a custom message and some do not. `ValidationOptions` should be a consistent trailing argument on every plugin.
- **`BuildTimeArrayAnalyzer` in array-type-analysis.ts** — `createTypedArrayValidator`, `generateOptimizedValidator`, `generateNestedLoopCode`, generating multi-dimensional loop code with `new Function`. Being CSP-safe was stated as an absolute requirement while this evaluated a code string. It is also entirely dead: array-batch-optimizer never sets `optimizedValidator`, nor `arrayStructure`. A multi-dimensional array can be written as a plain recursive loop.
- **`parseArrayElementPath` in nested-array-processor.ts** — an ad-hoc cascade of regular expressions — **and the validator lookup downstream of it**, which walks `fullFieldPaths` linearly and matches with `fullPath.includes(elementField)`, taking the first validator it finds. Path resolution by substring match is guesswork, and it is why `users[*].addresses[*].street` produced the path `users.addresses[0].street`, having dropped the outer index, with the wrong code (`required` where `stringMin` belonged). A path should be parsed into a proper syntax tree of segments and wildcards, and validators looked up by a structured key.
- **Reaching an array element through dot notation, as in `items.name`** — the "implicit array element access" branch of `TypeOfPath` and the older tests built on it. `NestedKeyOf` only ever produces `items[*].name`, and the run-time array batching assumes `[*]`. Dot notation is rejected by the types while remaining in `TypeOfPath`, so two representations coexist. Element access should be `[*]` and nothing else.
- **Three separate plugin mechanisms: composable, composable-conditional and composable-directly**, whose `attachComposablePlugin` in composable-plugin.ts touches a `builder._executionPlan` that does not exist. tupleBuilderPlugin is the mechanism's only user and fails at `build()` with a TypeError, so tuple validation does not run a single line. A plugin taking child builders should be expressible within the standard mechanism; a second mechanism was not worth it.
- **objectAdditionalProperties requiring known properties to be typed into `options.allowedProperties`.** The user has already declared those properties with `.v("user.name", ...)` and is made to write the same list again. The known-key set should be derivable from the declared fields, or at the least not require declaring them twice.
- **Three separate cut-down JSON Schema checkers**, one each inside arrayContains, objectAdditionalProperties and objectDependentSchemas (`validateAgainstSchema`, an inline type check, and `validateAgainstJsonSchema`). Three mutually different incomplete implementations of one job, supporting different keywords, behaving differently, and none of them recursing. JSON Schema evaluation belongs in one place.
- **objectPatternProperties applying only the first matching pattern and breaking.** JSON Schema's patternProperties applies every matching pattern, so this is not Draft-07. Claiming Draft-07 compatibility means matching the specification.
- **arrayUnique switching comparison method at length 10**, between a `===` double loop and a Set. It makes the answer for duplicate NaN depend on length. Decide the definition of equality first — SameValueZero, or deep equality — and implement it one way.
- **objectPlugin's code `"type_mismatch"` and message `"Not an object"`**, which contains neither the path nor the value, **and its overlap with the `objectType` the `b.object` slot injects.** Choosing `b.object` already runs objectType, so `.object()` is nearly redundant. Pick one, and put the path in the message.
- **The unused imports at the top of nearly every array and object plugin file** — importing `VALID_RESULT`, `INVALID_RESULT` and `ERROR_SEVERITY` and never using them — **and the comments claiming "V8 Optimization" and "monomorphic"** with nothing behind them. Between them they take up most of some files. The `@luq-plugin` documentation blocks (name, category, description, allowedTypes, params, returns, since) are worth keeping as a specification, and that form is carried forward.
- **arrayIncludesPlugin's `category: "arrayElement"`.** Its own documentation says standard, and category changes no behaviour at run time — the only branch on it is the composable check.
