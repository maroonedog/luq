# plugin-contract

The whole library is one idea: a plugin is a *named, tree-shakable value object* `{ name, methodName, allowedTypes, category, create() }` produced by the `plugin({...})` factory, and a validator is built by (a) collecting plugins into a bag keyed by `name`, (b) for each field, choosing a type entry point (`b.string`, `b.number`, ...), (c) attaching every plugin whose `allowedTypes` includes that type onto the chain under its `methodName`, and (d) calling each chained method to produce a **hoisted validator descriptor** — a plain frozen-shaped object `{ check, code, getErrorMessage, params, ...flags }` — which is appended to a per-field validator array (or, for `category: "transform"`, to a per-field transform array). Execution is then a flat loop over that array. No `eval`/`new Function` in the plugin path (one CSP violation exists elsewhere, see doNotInherit).

The single most important finding: **`category` is almost entirely a type-level device, not a runtime one.** At runtime the field builder distinguishes exactly three things (src/core/builder/context/field-context.ts:311-365): `category === "transform"` → push to `transforms`; `category.startsWith("composable")` → hand off to `attachComposablePlugin`; everything else → push to `validators`. And `category === "builder-extension"` never reaches the field builder at all — it is consumed one level up in `Builder().use()` (src/core/builder/core/builder.ts:73-92). So `standard`, `conditional`, `fieldReference`, `multiFieldReference`, `arrayElement`, and `context` are **runtime-identical**; they differ only in the method signature the type system exposes on the chain (`ExtractPluginMethodsByCategory` / `MapPluginMethodsToChainable` in plugin-types.ts). Any conditional/skip behavior is carried by *extra properties on the returned descriptor* (`shouldSkipAllValidation`, `skipForNull`, `skipForUndefined`), not by the category.

Second finding: `src/core/registry.ts` is **not** a second implementation. It is a 13-line re-export barrel over `src/core/registry/plugin-registry.ts`. There is exactly one registry implementation.

Third finding: the declared `ValidatorFormat` interface (plugin-interfaces.ts:26-69) and what the engine actually reads have drifted badly. Six declared markers (`__isFromContext`, `__contextOptions`, `__isStitch`, `__stitchOptions`, `__isOrFail`, `__condition`) and two declared flags (`isOptional`, `isNullable`) are **never read by any runtime code** — grep-verified. Meanwhile the engine reads three properties that `ValidatorFormat` does not declare (`shouldSkipAllValidation`, `messageFactory`, `__isCoerce`), and detects optionality by string-matching `validator.name === "optional"` (validator-factory.ts:106, 1852). The new contract must be closed: every property a plugin may return must be declared, and every declared property must be honored.

## 振る舞い規則

- `plugin({ name, methodName, allowedTypes, category, impl })` takes exactly five required fields and returns a plain, frozen-in-spirit value object. It must perform no registration, touch no module-level mutable state, and read no globals — a plugin module's only effect is to define a const.
- `name` is the identity: the dedup key in Builder.use and PluginRegistry.use, the key of the plugin bag, and the fallback error code when a descriptor omits `code`. `methodName` is the user-facing chain identifier and is deliberately allowed to differ from `name` (stringMin → `.min`, arrayMaxLength → `.maxLength`, objectAdditionalProperties → `.additionalProperties`).
- `create()` is invoked once per (field, type entry point) at attach time; the function it returns is invoked once per user chain call with the user's arguments and must return the descriptor. Any per-plugin precomputation (compiling a regex, resolving messageFactory, resolving code, building a field accessor) belongs in the impl body, before the descriptor literal — this is the 'hoisting' the whole design is named around. Nothing may be computed inside `check`.
- There are exactly 11 category values. At runtime only four behaviors exist: `transform` diverts the descriptor to the field's transform list; the three `composable*` values select the composer protocol; `builder-extension` is consumed by Builder.use and never reaches a field; and the remaining six (`standard`, `conditional`, `fieldReference`, `multiFieldReference`, `arrayElement`, `context`) are handled identically as validators. A plugin author picks among those six purely to request a particular typed method signature on the chain.
- A validator descriptor MUST provide `check`, `code`, `getErrorMessage`, and `params`. `check` is a pure boolean predicate that never throws and never mutates. `getErrorMessage` is called only after `check` returns false. `params` is the user's raw arguments, retained for message-context reconstruction.
- A type-narrowing plugin returns `true` from `check` for values of the wrong runtime type, so only the implicit type guard reports the type error and one bad value does not produce a cascade of unrelated messages. Every string/number/array plugin in the catalog follows this.
- A cross-field plugin (`fieldReference`, `multiFieldReference`, `conditional`, `context`) receives the root object as `check`'s second argument. It must behave deterministically when that argument is absent — the catalog's two established conventions are 'fail closed' (compareField returns false) and 'pass through' (validateIf, orFail, requiredIf return true, i.e. do not block).
- Null/undefined policy is expressed by two descriptor flags, not by category: `skipForUndefined` and `skipForNull`. If any validator on a field carries `skipForNull` and the value is null (likewise `skipForUndefined`/undefined), the whole field short-circuits to valid AND its transforms are skipped, returning the original value untouched.
- Conditional control flow is expressed by one descriptor hook, `shouldSkipAllValidation(value, allValues, arrayContext)`. Returning true aborts the remaining validators for that field. Validators declared BEFORE the conditional one have already run — the new engine must decide and document whether that ordering dependence is intended (see openQuestions).
- `allowedTypes` gates twice, identically: the type system removes the plugin from the chain type for non-matching type entry points, and the runtime declines to attach the method. Both gates must agree; a method that appears in the types must exist on the object.
- Two plugins may share a `methodName` if and only if their `allowedTypes` are disjoint — this is the designed mechanism behind `b.string.min` vs `b.number.min`. Overlapping methodName+allowedTypes must be a loud error at `use()` time, not a silent last-wins overwrite.
- `allowedTypes: undefined` means 'applies to every type'. Whether the new `plugin()` permits omitting `allowedTypes` at all is a decision to make deliberately; today `plugin()` requires it while the `TypedPlugin` interface marks it optional.
- Each type entry point prepends its own implicit type guard before any plugin validator. `union` and `tuple` get none. Every implicit guard passes null and undefined through, delegating that policy entirely to required/optional/nullable.
- `Builder().use(p)` mutates and returns the same builder (types accumulate, the value does not), dedupes by `name` first-wins, and rejects a non-object or nameless argument with a thrown error. `PluginRegistry.use(p)` is the opposite: it copies its map and returns a new registry, so a shared base registry can be branched safely. Both behaviors are intentional and both should survive — but the asymmetry must be documented rather than discovered.
- A `builder-extension` plugin's method is invoked with `this` bound to the Builder, which is how `fromJsonSchema` reaches `this.for()`. If the new design forbids `this`-dependence, `extendBuilder` must instead receive and close over the builder.
- Transforms run only in parse mode, only after every validator on the field has passed, in declaration order. Validate mode never runs them.
- Plugin modules must remain individually importable via `@maroonedog/luq/plugins/<name>` with `sideEffects: false` intact: no top-level registration, no import of a catalog barrel, no shared mutable module state.
- No `eval` and no `new Function` anywhere in the plugin or validation path.

The switch does nothing except cost bundle size and mislead readers into thinking category has runtime meaning at creation time. The only real work in that function is injecting `pluginName` into the result.
- **Injecting `pluginName` into the descriptor by wrapping the impl and spreading the result (`{ ...result, pluginName }`)** — It allocates a second object per chain call, defeats the 'hoisted, pre-shaped descriptor' goal by producing a different hidden class than the plugin literal, and exists only to supply an error-code fallback the plugin already knows. The new design should just make `code` default to `name` at attach time, without re-shaping the descriptor.
- **Six declared-but-dead ValidatorFormat markers: `__isFromContext`, `__contextOptions`, `__isStitch`, `__stitchOptions`, `__isOrFail`, `__condition`** — Grep-verified: no runtime code anywhere in src/ reads any of them. fromContext, stitch, and orFail all work purely through `check`/`getErrorMessage`. They are dead weight that makes the contract look richer than it is.
- **Two declared-but-dead flags `isOptional` and `isNullable`, alongside their working twins `skipForUndefined`/`skipForNull`** — Nothing reads them. Worse, the engine determines optionality instead by string-matching `validator.name === "optional"` (validator-factory.ts:106, 1852) — hardcoding a specific plugin's name into the engine, which breaks the moment someone writes their own optional-like plugin. One declarative flag must be the single source of truth.
- **Two declared-but-dead conditional hooks `shouldSkipValidation` and `shouldSkipFurtherValidation`** — field-context.ts:424-435 dutifully copies them onto the validator; unified-validator only ever calls `shouldSkipAllValidation`. `SkipFurtherValidationFlag` in core/plugin/types.ts documents a 'skip validations but not transforms' semantic that is not implemented anywhere. Either implement it or delete the concept — do not ship the declaration again.
- **The parallel legacy plugin return format `(value, ctx) => { valid: boolean; message?: string }`, and the `ValidationFunction` / `ValidationResultWithFlags` / `ValidationFlags` type-guard family built around it** — Every `PluginImplementation` type is a union of 'legacy function form | ValidatorFormat', which forces `extractCheckFunction` to branch at attach time and doubles the type surface. Zero plugins in the catalog use the function form. One descriptor shape, no union.
- **`__isCoerce` / `coerce`, `__isDefault` / `default`, `__isPreprocess` / `preprocess`, and the `PreprocessorPluginImplementation` type** — `extractTransformFunction` reads `__isCoerce` which `ValidatorFormat` does not even declare; `PreprocessorPluginImplementation` maps from a `"preprocessor"` category that is not a member of `PluginCategory`, so that branch of `PluginImplementation` is unreachable. No plugin in the catalog produces any of them. Dead pre-processing subsystem.
- **The composable-plugin helper library: `createValidatorResult`, `createSingleValidatorResult`, `createValidator`, `mergeValidatorResults`, `createCompositionBuilder`, `ValidatorDefinition`, `CompositionBuilder`** — A parallel, incompatible validator shape (`{ check(value, currentValue), name, inputType, outputType, metadata }` — no `code`, no `getErrorMessage`, no `params`) living alongside ValidatorFormat. `createValidatorResult`'s default validate loop is outright broken: it iterates `transforms.length` while indexing `validators[i]`. `mergeValidatorResults` and `createCompositionBuilder` have no callers. Composability is worth keeping; this second validator vocabulary is not.
- **Three distinct composable category strings (`composable`, `composable-conditional`, `composable-directly`) and three creator functions** — `createComposableConditionalPlugin` and `createComposableDirectlyPlugin` both literally call `createComposablePlugin` and spread-override the category string. The runtime branches on `category.startsWith("composable")` and the type level treats all three as one union member everywhere. Three names for one behavior.
- **`attachComposablePlugin` (composable-plugin.ts:392-450)** — It rebuilds the composer result on every chained call, contains a dead `if` branch guarding a `// TODO: Restore complex validation logic` comment that does nothing, and reaches for a `builder._executionPlan` that the current field builder never creates — so the fallback path dereferences `executionPlan.addValidator` on undefined. It is broken, not merely ugly.
- **Eagerly constructing all nine type builders per field in `createOptimizedFieldContext`, each re-running `plugin.create()` and attaching every allowed method** — With N plugins that is 9N `create()` calls and 9N closure allocations for a field that will use exactly one type. It also means a plugin's `create()` must be cheap and idempotent for reasons the contract never states. Lazy or single-type-selected construction removes the constraint entirely.
- **Silent error swallowing in `attachPluginMethods` (`catch (e) { /* Plugin error - ignore silently */ }`) and `extractCheckFunction`'s `return () => false` for a descriptor with no `check`** — A malformed plugin produces a field that always fails validation with no diagnostic anywhere. A contract violation must throw at attach time with the offending plugin's name.
- **The engine's hardcoded per-plugin knowledge: `validator.pluginName === "stringStartsWith" | "stringEndsWith" | "stringMin" | "stringMax" | "arrayMinLength" | "arrayMaxLength"` producing message context (unified-validator.ts:1296-1332), `v.name === "optional" | "required"` (validator-factory.ts), `methodName === "transform" || methodName.startsWith("to")` (strategy-factory.ts:554-556)** — Every one of these is the engine reaching into the plugin catalog by string. It defeats the plugin abstraction, silently misclassifies any user plugin whose method happens to start with 'to', and means a third-party plugin can never get first-class treatment. Message context must come from the plugin's own `params`/`getErrorMessage`; transform-ness must come from `category` alone.
- **`src/core/optimization/core/validation-engine.ts` as a second execution engine** — It implements the full descriptor contract INCLUDING the three-argument `check(value, allValues, arrayContext)` and four-argument `getErrorMessage`, but nothing imports it except a single type (`ValidationField`). It is dead code that contradicts the live engine, which passes only two arguments and never plumbs arrayContext at all. Exactly one engine in the new tree.
- **`arrayContext` as a declared parameter of `check`, `getErrorMessage`, and every conditional plugin's condition** — It is threaded through the types and through optionalIf/requiredIf/validateIf, but grep shows no live code path ever constructs or passes one — only the dead validation-engine.ts references `context.arrayContext`. Either implement per-array-item context for real, or drop the parameter. Shipping a documented parameter that is always undefined is worse than not having it.
- **`src/core/registry.ts` as a separate file** — Thirteen lines, 100% re-export of `./registry/plugin-registry`. It is the reason the two files look like duplicate implementations; they are not. One file, one path.
- **`FieldRule.validate` / `FieldRule.parse` as written (plugin-registry.ts:444-657)** — They implement a THIRD, divergent execution semantics: they call `validator.check(value, context)`, ignore `getErrorMessage` entirely (falling back to `messageFactory` or the literal string 'Validation failed'), ignore `skipForNull`/`skipForUndefined`, ignore `shouldSkipAllValidation`, and use `validator.name` as the error code instead of `validator.code`. They also rebuild the entire field context and re-execute the user's definition function on every single call. FieldRule must run the same engine as everything else.
- **`WithPluginName<T>` and the pervasive `any` in the contract types — `TImpl extends Function`, `TMethod extends Function`, `(...args: any[])`, `params: any[]`, `check: (value: any, allValues?: any) => boolean`, `impl: stitchImpl as any`** — `Function` and `any` are banned by the new standards, and here they are load-bearing in the contract itself: `TypedPlugin.create(): TMethod extends Function` is what forces every downstream mapped type to re-widen. The new contract must express the plugin method as a concrete generic call signature so `unknown` + narrowing works end to end.
- **Three files all exporting `stitchPlugin` (stitch.ts, stitch-typed.ts, stitchSimple.ts) and two exporting `fromContextPlugin` (core/plugin/fromContext.ts and core/async.experimental/from-context-plugin.ts)** — Duplicate plugin identities with the same `name` — whichever import a user reaches for wins, and Builder.use's name-dedup will silently drop the second. One plugin, one name, one file.
- **`new Function(...)` in src/types/array-type-analysis.ts:196-212 (`createNestedLoopValidator` generating nested loop source)** — It directly violates the stated CSP-safe guarantee. It is reachable from validator-factory.ts, which imports from that module. Whatever nested-array performance it was chasing must be achieved with real recursion or precomputed accessors.
- **`plugin.name` used as a fallback error `code` via a runtime `||` chain (`validator.code || validator.pluginName || "VALIDATION_ERROR"`) repeated at five call sites** — The default belongs in one place, applied once when the descriptor is normalized at attach time, so the execution loop reads a single always-present field.
- **`PluginCategories` const object (plugin-interfaces.ts:394-472)** — A runtime object holding `description` strings, `examples` arrays, and `{} as SomeType` phantom fields, whose only consumers are two type helpers that could read the types directly. It ships documentation strings into every bundle that imports plugin-interfaces.
