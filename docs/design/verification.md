# The design's verification record

This design went through two repair rounds and was verified by actually compiling the TypeScript.

## Blockers resolved

- A1 - PluginSignature's third parameter now defaults to `unknown`, not `Unchanged`. With the old default, AnyPlugin pinned `out` to "unchanged" and every presence/transform/guard plugin failed the definePlugin constraint with TS2344. Verified: a `readonly AnyPlugin[]` holding one plugin of each of the eight kinds compiles with no cast.
- A2 - build() receives RUNTIME arguments, not the marker tuple. New L2 module `runtime-args.types.ts` maps FieldRef->string, FieldRefs->readonly string[], RootPredicate/RootReader/SelfReader/SelfGuard->functions over `unknown`, SelfValue->unknown, ElementChain/NarrowedChain->readonly Rule[]. L2 stays root-agnostic; nothing there names TRoot.
- A2b - `out` now also constrains build's RETURN type via RuleForOut: TransformOut demands a TransformRule, any PresenceShift demands a PresenceRule, everything else stays the full Rule union. `RuleForOut<unknown>` is `Rule`, so AnyPlugin is unaffected.
- A3 - the concrete plugin bag B is threaded through ResolveArg/ResolveArgs/ChainMethod into FieldSlots for ElementChain and NarrowedChain. Without it SlotPlugins collapsed to `{[x:string]: AnyPlugin}` and every nested-chain call type-checked, including invented methods, wrong arity and unregistered plugins.
- A4 - CompositeRule's `select(value, ctx): number | IssueDetail` is replaced by `combine(runners): CompositeExecute`, called ONCE at build time. That is what makes all-apply (allOf), positional (tuple), existential (contains), scatter (patternProperties) and routing (if/then/else) expressible by one rule kind. CompositeBranch is now a real type `{label, rules, fields}`.
- A4b - RecursiveRule is the sixth Rule kind. Recursion could not be a composite because its 'branch' is the plan being compiled. compileSchema back-patches a PlanRef, resolveRecursion turns the rule into CompiledField.recursion, and runtime re-enters its own runPlan with a depth counter and a WeakSet cycle guard. The plugin contains zero execution logic.
- A4c - the BranchExecutor port (declared L4, implemented L5, wired L6) lets compile hand `combine` real branch runners without importing upward. Branch execution is provably runPlan; compile grows no second traversal loop.
- A5 - union guard exhaustiveness is carried in ChainState.covered rather than in a third type parameter, so FieldChain/ChainMethod keep their arity. `.guard()` is synthesised from `out: GuardOut` exactly as `.transform()` is from TransformOut. `.v()` returns UnionGuardCoverageError instead of the builder when members remain uncovered; a chain that declares no guard is never checked.
- A6 - the two JSON Schema bundle plugins move to `src/json-schema/extensions/<dir>/`, tier `extension` (may import json-schema modules and plugin ENTRY files). `src/plugins/<dir>/` is tier `isolated` with a closed allow-set and no exception list. Public subpaths ./plugins/jsonSchema and ./plugins/jsonSchemaFullFeature are unchanged. The isolation checker must NOT treat src/json-schema/** (outside extensions/) as a plugin directory.
- B1/B2 - the plugin count is 71, derived from a measured 73 legacy `export const *Plugin` symbols (not the 72 previously claimed): stitch.ts, stitch-typed.ts and stitchSimple.ts are three implementations of one responsibility and merge to one (-2). conditionalSchema, which had no destination in any build step, gets src/plugins/conditional-schema/. 78 was never a plugin count; it is the package.json#exports key count (6 fixed + 71 subpaths + 1 compat alias).
- B5 - RuleBuildContext gains `fieldPath` and `declaredSiblingKeys`, computed by L4 from declared PATH STRINGS alone and Object.freeze()d (readonly is erased at run time; an unfrozen shared array was actually mutated by a plugin in the proof). objectAdditionalProperties defaults to it and an explicit `allowedProperties` option wins. The core never learns a plugin by name and no import direction changes.
- B6 - one descent rule (`IsOpaqueObject`) read by both FieldPath and ValueAtPath, `[*]` as the only array wildcard, unions re-distributed, `unknown extends T` tested BEFORE NonNullable (NonNullable<unknown> is `{}`), one shared depth budget decremented on every segment including `[*]`, and LeafPath generated structurally to replace the unimplementable `Exclude<FieldPath<T>, TDone>`.
- C1 - primitive slots carry the real field type (ValueAtPath), so presence type-state is observable: `.required()` strips undefined from a later transform callback and `.optional()` does not. A slot unrelated to the field type resolves to SlotTypeMismatch, a readable error object rather than a silently permissive chain.
- C2 - a JSON Schema keyword can only be bound through bindKeyword(slot, pluginObject, toArguments), so the method literal is produced by the plugin itself and `"minItems"` is unwritable. Bindable plugins are restricted to marker-free ones via IsMarkerFree, because a marker's resolved form depends on TRoot and a schema has no TRoot.
- D - the 24-step list becomes a 32-step graph with one author per path, derived artifacts that are git-ignored (so branches cannot conflict over them) or refreshed only at a gate, plugin steps confined to their own directories, and stage boundaries crossed only through a gate.
- CONTRADICTION A-1 - ResolveOut's presence shifts use the NAMED ChainState operators, not inline object literals. The inline form silently drops `covered` and erases every recorded guard; both original repairs missed it because both wrote `.required()` BEFORE `.guard()`. Mutation-verified: restoring the inline literal makes the guard-then-required test stop failing (TS2578).
- CONTRADICTION A-2 - ElementChain/NarrowedChain resolve EAGERLY to `readonly Rule[]`, not to a thunk. The 'user callback runs exactly once' invariant belongs to src/chain/collect-branch-rules.ts, not to plugin-author discipline.
- CONTRADICTION A-3 - no plugin contains a traversal loop. The arrayEach draft that looped over elements itself (and silently discarded presence/gate/transform rules) is gone; element-scoped plugins are composites whose branches the engine runs.
- CONTRADICTION A-4 (new defect, found only by integrating) - an OPTIONAL marker argument (`then?: ElementChain`, `rest?: ElementChain`) makes A[I] be `M | undefined`, which matched no marker branch and leaked the raw marker into build(). Both resolvers now strip `undefined` before matching and re-add it after. Pinned by conditionalSchemaPlugin in the contract fixtures.
- CONTRADICTION A-5 - RuntimeArg's array recursion is a MAPPED type, so `readonly [number, string]` stays a tuple instead of widening to `readonly (number|string)[]`.
- CONTRADICTION A-6 - all resolver branches are non-distributive. The original justification for this was wrong (a plain union argument survives either way; verified by flipping all branches) but the conclusion is right: ResolveOut, ChainMethod's `out` discrimination and RuleForOut must all be non-distributive, and having one rule instead of two is worth it. Consequence, now stated as spec: a marker may not be declared inside a union argument.
- CONTRADICTION A-7 - RuleBuildContext is generic over the plugin's own message context AND carries fieldPath/declaredSiblingKeys; messageFactory stays OPTIONAL so a plugin without one falls back to its own describe(). MessageContextExtra is `object`, because `Record<string, unknown>` rejects an interface with no index signature.
- CONTRADICTION A-8/A-9/A-10 - one naming and one shape for rule construction: `buildMessageContext(detail): C` (verb phrase; `contextOf`/`toContext` were both noun phrases and both violated the standard), spec-object arguments everywhere, `fail(detail: IssueDetail)`, and `definePlugin<{args;out;context}>()` (the two-parameter form cannot express `out`, so neither RuleForOut nor the transform/guard chain discrimination would work).
- CONTRADICTION A-11 - ElementOf is its own L1 leaf module, used by field-path, value-at-path, leaf-path and the chain, so there is exactly one array-unwrapping rule.
- CONTRADICTION A-12 - test placement follows F-E-C2, not D: test/unit, test/type, test/integration, test/contract, bench/, tsconfig.type-test.json, one new devDependency (expect-type). D itself said this was the F owner's call.
- CONTRADICTION A-13 - the uuid -> string-uuid rename is reverted. Directory, subpath, symbol and method all stay `uuid`, which removes a subpath override and a docs rewrite.
- CONTRADICTION A-15 - tupleBuilder takes `(positions: readonly ElementChain[], rest?: ElementChain)`. The competing variadic form used a non-marker `ElementRuleRunner`, which the chain cannot resolve, so no call-site type could be produced for `b.tuple.builder(...)`.
- ~~NEW - `.each()` / arrayEach does not exist and is not being added.~~ **Withdrawn during implementation.** `.each()` is universal quantification (Draft-07's `items`) and `.contains()` is existential (some number of elements must match); the two mean different things. What this item called "the same negation" was about a handful of type-test counterexamples, not about run-time meaning. Beyond that, a path declaration cannot be written inside a sub-chain, so `.each()` is the only way to constrain array elements universally within patternProperties or dependentSchemas — and the JSON Schema layer already depends on it. **src/plugins/array-each/ stays.**
- NEW - `.required()` narrows the TYPE the same way it validates. The legacy PresenceRule rejects undefined AND null AND "", but PresenceShift had only single-flag kinds, so the type kept `| null`. A fourth kind `excludeMissing` (both flags false) is added to the registry, which forces branches in ResolveOut and is checked by the coverage proof.
- NEW - AnyChain's phantom must be `ChainMarks<unknown, ChainState>`; `never` makes no concrete chain assignable to it.
- NEW - Validator exposes both validate() and parse(), both returning ValidationResult<T>. validate never transforms; parse applies transforms in declaration order over a copy-on-write structure.

## Risks that remain

- Only the TYPE layer is proved. Everything in coreTypeDesign compiles and the 10 negative assertions are mutation-verified, but no runtime code has been written or executed: the chain node's guard/transform arity, collect-branch-rules' once-only invariant, compileComposite's back-patching, run-branch's RunState allocation and run-recursion's cycle guard are all designs, not measurements. The first real risk of the rebuild lives there, not in the types.
- The instantiation budget is one measurement on one machine with one chain shape. 89,190 instantiations over 45 plugins x 100 fields x 25 steps was measured BEFORE the extra bag parameter, before ChainState grew `covered`, before SlotAccepts/SlotValue were added to every slot, and before ConverterChain/BindableMethod existed — and the harness's 45 plugins were all `out: Unchanged` with one number argument, i.e. the cheapest possible shape. A chain that mixes transforms, guards and presence shifts creates more distinct FieldChain instantiations. This must be re-measured at the chain-types step (6) with a mixed-marker chain and with the real 71-plugin bag, and IDE completion latency measured with it. If it is bad, the lever is FieldSlots, not the marker design.
- ConverterChain has never been compiled side by side with the real FieldChain. The claim 'ConverterChain<S> is a faithful slice of FieldChain for marker-free methods' is reasoned, not verified, and it is also literally false in one respect today: ConverterChain omits the trailing `options?: RuleOptions<C>` that ChainMethod appends to every call. It is a strict subtype for calls that pass no options, which is all the converter does now, but a schema-driven custom message would need it. One type test closes this and it must be added at step 24.
- The marker coverage proof shows each resolver HANDLES every marker; it does not show the two resolutions are semantically PAIRED. The stronger check (the erased call-site type must be assignable to the runtime type) fails legitimately on RootPredicate under strictFunctionTypes, so FieldRef->string, FieldRefs->readonly string[] and the rest are still reviewed by eye. A wrong pairing would compile and would only surface at run time.
- Guard coverage is compared against the chain's FINAL value type. If a `.transform()` runs after the guards, TValue has already been rebound and the exhaustiveness check compares against the transformed type. There is no test for guards-then-transform and it is not fixed; the robust form snapshots the guard subject into ChainState at the first `.guard()`. Guards-then-presence IS fixed and tested.
- The union-guard coverage error surfaces one call late: `.v()` returns UnionGuardCoverageError, so the squiggle lands on the following `.build()` rather than on the incomplete `.v()`. Moving it onto the chain itself (via an intersection in the callback's declared return type) made inference of C unreliable, so it was not shipped. Acceptable DX, not ideal.
- `SlotValue` uses Extract, so on a genuinely-union field typed `string | number`, `b.string` silently narrows to `string` rather than erroring. That matches the type-tolerant runtime (a non-string passes the check) but it is a judgement, not a ruling.
- Presence type-state is declaration-truth, not wire-truth. For a field declared `name: string`, `.optional()` still produces `value: string` in a transform even though the runtime may hand it undefined for a missing key. The alternative (open state means TField | undefined) makes `.required()` produce `string | null` and is worse. Nobody has been told this yet; it belongs in the migration guide.
- Index-signature subtrees are unchecked by construction. `meta.${string}` is a template literal type, so it also accepts `meta.a.b` and `meta.a[*]`, and ValueAtPath returns `unknown` for all of them — deliberately, otherwise the round-trip property fails. No depth limit and no key checking inside a Record<string, unknown>. This is the price of the fromJsonSchema default and it must be documented as an escape hatch rather than left looking like type safety.
- OpaqueObject is a closed list. Anything a user models with a built-in that is not on it (Intl.*, URL, Temporal, a Node Buffer subclass beyond ArrayBufferView) will be descended into and its members become paths. Adding an entry is one line with no other effect, but there is no automatic detection.
- Function-typed properties are generated as leaf paths, so `.strict()` demands a declaration for a callback field. Validating a callback is arguably meaningless. I left them in because excluding them is a policy choice rather than a correctness one, and because one descent rule is worth more than one exception.
- Symbol and numeric keys are not addressable anywhere (`Extract<keyof T, string>` drops them), so a model keyed by numbers cannot be validated per field. Legacy had the same limitation, so it is not a regression — but nobody has ever stated it.
- Concrete tuple indices are not part of the grammar: `tup[0]` is neither generated nor resolved, and a tuple's elements are reachable only as `tup[*]`. If tupleBuilder needs per-index typing it must come from the composite branch API, not from a path literal. That has not been designed.
- Every composite branch is a full nested ValidationPlan, and run-branch allocates a RunState per branch attempt. For anyOf over many alternatives inside a hot loop this will show against the 43K ops/sec complex target. A pooled or reusable run state is the fix; the shape does not need to change, only the allocation. Nobody has profiled it.
- `combine` is a function stored on the rule and carried into the plan. Nothing structurally prevents a plugin closing over mutable state and making two validators built from the same rule interfere. The only defence is the documented contract ('combine must be pure and is called once') plus review; no lint rule exists.
- abortEarly inside a composite branch is hardcoded true. Right for anyOf/oneOf, where only a verdict is needed; debatable for allOf, where a user might want every failure inside the branch. Exposing it means widening the BranchExecutor port.
- The three stitch implementations are recorded as one merge, but nobody has verified they are actually reconcilable under the corrected marker resolution. stitch.ts is 202 lines with typed field paths, stitch-typed.ts and stitchSimple.ts differ in call shape. If the merged plugin cannot express all the shapes, the count becomes 72 or 73 and the catalog lock, the export-key count and the migration guide all move.
- The 57-subpath preservation list was transcribed from package.json#exports on the current working branch, not from the published npm tarball. If 1.x shipped a subpath that has since been removed from package.json, the list misses it and check-legacy-subpaths will not catch the regression.
- classifyImport in the isolation checker is proved only against already-resolved paths. The real script must resolve TypeScript specifiers first (relative paths, tsconfig paths, extensionless imports, type-only imports, dynamic import()) and that resolution step — where isolation checkers usually leak — has not been built or tested. It is also undecided whether `import type` from a forbidden area counts as a violation (it is one by design; it emits no runtime dependency).
- Git-ignoring the generated manifest makes a merge conflict impossible but means a fresh clone cannot typecheck until `npm run generate` has run once, and editor tsserver instances that start before the prestep will show phantom missing-module errors. The wiring is specified but has not been built or tested. The failure is noisy, not silent.
- package.json region ownership (#!/exports authored once, #/exports regenerated at gates) rests on a generator that must preserve key order and every other field byte for byte. That generator has not been written. If it reformats the file, the ownership guarantee is void.
- The whole type set is verified against TypeScript 5.8.3 only. The `${infer K}[*]` last-occurrence inference, `NonNullable<unknown> = {}`, method bivariance carrying AnyPlugin, and the `[A] extends [B]` non-distribution idiom are all version-sensitive behaviours. The TypeScript version must be pinned in package.json and this whole suite re-run on any major bump.
- `declaredSiblingKeys` sees only declared PATH STRINGS. If the chain can ever introduce child declarations that never appear as a top-level path, objectAdditionalProperties will under-report its known keys there. This could not be resolved without the final chain runtime and needs a test at step 21.

## Items needing a decision from the maintainer

- NESTED ISSUE PATHS (public result shape — I could not decide this for you because it changes what consumers see). When a composite branch fails, its child issues are currently attached as `IssueDetail.causes` on ONE parent issue, so an allOf failure on `profile.name` reports at path `profile`. The alternative is to splice the child issues into the top-level `issues` array with the parent path prefixed, which gives much better DX but changes the issue COUNT and the paths that existing 1.x tests and consumer code assert on. Both are implementable; the shape must be chosen before the compile step (step 10) because run-branch.ts is written to it. My recommendation is splice-with-prefix, with `causes` kept for anyOf/oneOf where no single branch is 'the' failure.
- GIT SUBMODULE FOR THE JSON-SCHEMA-TEST-SUITE. I chose a pinned submodule after disproving the npm route (@json-schema-org/tests is from 2020 and depends on a git URL). Some organisations forbid submodules in CI or in vendored builds. If yours does, say so now and I will switch to a pinned vendored copy under test/fixtures with a SHA file and a refresh script — it costs about 3 MB in the repo and one extra review step per suite bump, and it changes step 1 and step 26.
- PATH DEPTH BUDGET = 6 (a.b.c.d.e.f.g is the deepest addressable path). Beyond it, a path is simply not offered and the truncated node counts as a LEAF for .strict(), so a user with a 7-level model gets silence rather than an error. Raising it to 8 measured ~6% more instantiations (117,608 -> 124,435) and ~0.13 s, so it is cheap. This is a product call about how deep your users' models actually are, and it is the one number in the path layer I did not want to pick for you.
- THE README THROUGHPUT CLAIMS (1.2M ops/sec simple, 43K complex). I have made them a reproduction TARGET and made CI gate on a runner-independent ratio instead, but nobody has measured the new engine yet. If the rebuilt engine lands, say, 15% below those figures, do you want the release blocked until it reaches them, or do you want the README restated from a fresh measurement on a named machine? This decides whether step 30 is a gate or a report.
- ONE NEW DEV DEPENDENCY: expect-type@^1.4.0 (types-only, zero transitive deps, nothing imported at runtime). The alternative is the 33-line in-repo assertion kit alone, which is enough structurally but gives noticeably worse error messages on value-shape assertions. If your policy is zero new dependencies, I will drop it and the type tests still work unchanged.
